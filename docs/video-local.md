# Видеозапись тестов на локальном стенде

Функция включается парой `VIDEO_ORGANIZATION_ID` и `VIDEO_CAMPAIGN_ID`. Для локальной проверки используйте отдельную базу с синтетическими участниками. Команда `npm run db:migrate` добавляет поля согласия и таблицу подключений. Остальные кампании работают по своим обычным правилам.

## Запуск

Понадобятся Docker Compose, FFmpeg с энкодером libx264 в PATH процесса API (либо переменная FFMPEG_PATH с путём к исполняемому файлу), веб-приложение и PostgreSQL. Добавьте в локальный `.env`:

```dotenv
VIDEO_ORGANIZATION_ID=demo-organization
VIDEO_CAMPAIGN_ID=demo-campaign
LIVEKIT_API_KEY=video-dev
LIVEKIT_API_SECRET=<случайный секрет длиной не менее 32 символов>
LIVEKIT_URL=http://127.0.0.1:7880
LIVEKIT_PUBLIC_URL=ws://localhost:7880
LIVEKIT_NODE_IP=<локальный IPv4 компьютера, доступный браузеру и Docker>
VIDEO_RECORDINGS_DIR=./.data/video-recordings
```

Запустите `docker compose -f compose.video.yml up -d`, затем API и веб-приложение из корня проекта. Если приложение уже запущено, перечитайте настройки перезапуском API. Сигнализация на стенде доступна через localhost, медиатрафик использует TCP 7881 или UDP 7882. При изменении адреса компьютера обновите `LIVEKIT_NODE_IP` и пересоздайте медиасервисы. Записи в каталоге хоста должны быть доступны для записи контейнеру Egress и для чтения и удаления API.

## Проверка

1. Войдите под участником с назначением в выбранной кампании. При первом входе примите согласие на видео, затем обычное согласие на данные, если оно ещё не принято.
2. Пройдите тренировку, нажмите «Начать тест», затем «Подключить камеру». После разрешения браузера дождитесь надписи «Идёт видеозапись». Сервер запускает новую попытку отсчёта времени после подтверждения записи. При возврате в уже запущенную попытку сохраняется исходный срок сдачи.
3. В другом профиле браузера войдите под администратором той же организации, выберите ту же кампанию и откройте «Видеозаписи». Нажмите «Смотреть эфир». Руководитель может выбрать участника по имени и тесту.
4. Выйдите из теста. После закрытия файла в архиве появится «Готовится MP4…», затем «Смотреть запись» и «Скачать MP4». Ссылка требует входа руководителя. Повторное подключение создаёт отдельный фрагмент с собственным временем и сроком хранения. Дата истечения видна в таблице. Временные файлы, прерванные задания и истёкшие записи обрабатываются фоновым процессом API.
5. Для проверки состава файла выполните `ffprobe -v error -show_entries stream=codec_type,codec_name -of json <файл.mp4>`. В файле должен быть один видеопоток H.264. Дата, редакция, язык и принятый текст доступны в событии журнала `video.consent`.

Браузер передаёт только изображение с камеры. При поддержке H.264 сервис записи сохраняет MP4 во время теста. После завершения записи API сверяет размер файла с данными LiveKit и открывает доступ администратору. Для камер, передающих VP8, сервис сохраняет WebM. Фоновый обработчик преобразует его в MP4. Архив удаляет исходник и готовый файл через три календарных месяца после окончания каждого фрагмента. При потере связи интерфейс предлагает переподключить камеру. Ответы сохраняются обычным механизмом теста, отсчёт времени продолжается.

При размещении приложения и видеосервера на разных машинах используются `deploy/video/compose.platform.yml` и `deploy/video/compose.worker.yml`. API читает архив через закрытое SFTP-подключение. Каталог `VIDEO_EGRESS_DIR` внутри Egress, `VIDEO_RECORDINGS_DIR` внутри API и том фонового обработчика должны указывать на одни и те же файлы рабочей кампании. Перед выпуском проверьте чтение файла с обеих машин. Для отдельного обработчика укажите в API `VIDEO_CONVERSION_WORKER=external`. На видеосервере обработчик использует локальный Redis и закрытое соединение с PostgreSQL, с правом чтения нужных полей видеосессии и изменения её статуса. Скачивание и просмотр требуют действующей сессии администратора организации.

Для эксплуатации потребуется проверить одновременные записи на выбранных серверах в Казахстане, закрытый каталог с достаточным местом, HTTPS/WSS и доступность медиатрафика из сети заказчика. Локальная конфигурация рассчитана на проверку функциональности.

## Подключение через домен AssessFlow

Браузер участника и кабинет администратора устанавливают соединение с LiveKit через `wss://<APP_DOMAIN>/camera-signal`. Видеопоток передаётся на видеосервер по WebRTC. В `/etc/assessflow-video/platform.env` укажите `LIVEKIT_URL=https://<VIDEO_HOST>` для серверного API и `LIVEKIT_PUBLIC_URL=wss://<APP_DOMAIN>/camera-signal` для браузеров. На площадке Даму используются `APP_DOMAIN=edukz.duckdns.org` и `VIDEO_HOST=93.171.233.85`. Сертификат видеосервера должен проходить проверку для указанного имени или IP.

При запуске с `compose.production.yml` и `deploy/video/compose.platform.yml` встроенный Caddy загружает маршрут автоматически. Задайте `APP_DOMAIN` и `VIDEO_HOST` в окружении Compose. Если площадка использует **общий Caddy**, скопируйте `deploy/video/caddy/signaling.caddy` в доступный ему каталог. Добавьте в блок сайта перед общим обработчиком:

```caddyfile
import /etc/caddy/assessflow-camera/signaling.caddy 93.171.233.85
```

При переносе укажите адрес своего видеосервера. Перед включением проверьте конфигурацию через `caddy validate` и примените её в паузе между видеосессиями. Запрос без токена к `/camera-signal/rtc/validate` должен вернуть HTTP 401. Для полной проверки опубликуйте видео в тестовой комнате, откройте прямой эфир из второго браузера и проверьте сохранённый MP4.

### Переключение работающей версии API

На площадке Даму для переключения без перезапуска API используется сервис `assessflow-video-access`. Он передаёт запросы выдачи доступа штатному API и заменяет старый адрес LiveKit в JSON для подключения камеры и просмотра эфира. Новая установка сразу выдаёт публичный адрес из `compose.platform.yml` и может работать с одним маршрутом сигнализации.

Чтобы воспроизвести конфигурацию действующей площадки, задайте `EXTERNAL_PROXY_NETWORK` равной существующей Docker-сети, общей для Caddy и API. Из корня репозитория запустите:

```sh
docker compose --env-file .env.production -f deploy/video/compose.camera-access.yml up -d
```

Скопируйте `deploy/video/caddy/credentials.caddy` в каталог конфигурации общего Caddy. Внутри существующего обработчика `/api/*` задайте порядок:

```caddyfile
handle /api/* {
    route {
        import /etc/caddy/assessflow-camera/credentials.caddy
        reverse_proxy api:4000
    }
}
```

Проверьте конфигурацию и примените её, когда участники завершат текущие сдачи. При стандартном имени проекта адрес API для сервиса — `assessflow-api-1:4000`. Для другого имени укажите `CAMERA_API_UPSTREAM`. Сервис доступен только в Docker-сети.
